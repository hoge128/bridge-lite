フィルタパイプライン再設計

bridge-lite  ·  最終更新: 2026-05-11  ·  LibraryStore.swift 主要変更ファイル

背景・動機

bridge-lite には多数のフィルタが実装されている。現状は動作しているが、 「フィルタを 1 つ変えるだけで全パイプラインが同期で走り直す」構造のため、 将来エントリ数が数万〜10 万件規模になったときに主スレッドが詰まる懸念がある。 体感上は現状困っていないが、将来の備えとして設計を整理する。

key insight: filter.matches() は visibleIDs 用に 1 回 + aggregates 6 軸分に 6 回 = 計 7 回フルスキャンされている。 aggregates の coalesce だけで主スレッド占有を大幅に削減できる。

現状のパイプライン構造

中心関数: LibraryStore.recomputeVisible() — すべてのステージを 1 関数で直列実行。

S1
Representative 選定
全 shotGroups を走査して代表エントリを決定。メモ化なし。filterKinds が変わっても変わっていなくても毎回全走査。
S2
述語フィルタ（matches() 直列評価）
現在の評価順: nameSearch → excludedExtensions → cameraOnly → excluded* → iso/focal/shutter/aperture → date（重） → ratings/labels → luminance
S3
Sort → visibleIDs
exifDate キーは DateFormatter parse が N log N 回（旧: キャッシュなし）。PR4 でキャッシュ化済み。
S4
Daily grouping（viewMode == .daily のみ）
rebuildDailyGroups() — visibleIDs 全件で photoDate() を呼ぶ。PR4 のキャッシュが効く。
S5
Aggregates（6 軸ヒストグラム + availables）
filteredIDsExcluding を 6 回呼び、matches が合計 7 回フルスキャンされる。最大のボトルネック。
トリガー問題: filter.didSet { recomputeVisible() } — coalesce なし。 ISO スライダーをドラッグするたびにフル 5 ステージが同期実行される。

実装状況（2026-05-11 時点）

PR1 完了 — filter.didSet 差分ディスパッチ

追加: FilterChangeShape / classifyFilterChange(from:to:) / onFilterChanged(from:)

  • repsAffected: flatten / filterKinds が変化 → S1 から再計算必要
  • isTextInput: テキスト/スライダー系 → coalesce 候補（13 フィールド）

現状: shape は計算済みだが coalesce は未使用。後続 PR でテキスト入力を 150〜200ms 間引く。

PR2 完了 — パイプラインのステージ分解

追加した主要要素:

  • PipelineDirty 構造体（5 フラグ）+ private var dirty
  • 中間キャッシュ 3 つ: cachedRepresentatives / cachedRepsOrdered / cachedFiltered
  • mark(...) — 下流フラグを自動伝搬
  • runDirtyStages() — 5 ステージを順番に実行
  • 5 ステージメソッド: runStageReps/Filtered/Sorted/Daily/Aggregates()

recomputeVisible() は全 dirty 立て + runDirtyStages() の薄いラッパに変更。21 か所の呼び出し元はそのまま。

最初の実効最適化: applyOrder() が mark(sorted: true) + runDirtyStages() になり、sort キー変更時に S1/S2/S5 をスキップ。

PR4 完了 — exifDateCache による日付パースのキャッシュ化
@ObservationIgnored private var exifDateCache: [UInt64: Date?] = [:]
// キー不在   = 未計算
// 値 nil    = datetime 未設定 or パース失敗確定

  • scheduleMetaFlush の flush 後に flushedExif を eager キャッシュ書き込み
  • photoDate(for:) をキャッシュ優先実装に置換（lazy fallback あり）
  • applyRemovalToStore / reset() でクリア追加

効果: exifDate ソートが N log N 回の DateFormatter parse → ほぼ全件 O(1) lookup。daily / date filter / aggregates も同様。

PR3 未実施 — Representative メモ化

computeRepresentatives が毎フィルタ変更で全グループ再走査。 RepsCacheKey(flatten, kinds, shotGroupsVersion, entryKindVersion) でメモ化し、 entryKindCache: [UInt64: PhotoKind] で isDevelopedMember の 4 段判定を O(1) に。

懸念: invalidate 漏れで古い representative が残る可能性。DEBUG アサーションで旧パスと比較後に切替。

PR5 未実施 — CompiledFilter（述語並び替え + パース済み値保持）

matches() を呼ぶたびに各フィールドをパースしている。 struct CompiledFilter: Sendable でパース済み値を保持し、 filter.didSet 時に 1 度だけ compiled() を呼んでメモ化。 4 Tier 述語メソッドに分割し、コスト昇順に並び替え。

PR6 未実施 — Aggregates の coalesce + Task.detached 化

aggregates（S5）を 200ms coalesce + Task.detached で非同期化。 AggregateInputs を Sendable な値型 snapshot として渡し、 結果反映時に scanGeneration 照合。

ユーザー許容: 200〜400ms の遅延は OK（確認済み）。最大の主スレッド占有削減効果。

PR7 任意 — Aggregates 1-pass 化

現在 filteredIDsExcluding を 6 回呼んでいる（= matches を 6 回フルスキャン）。 axis-aware predicate で 1 ループに統合。PR6 の後で性能計測して効果が見えてから判断。

将来の議論ポイント

1. filter.isTextInput の coalesce 有効化

onFilterChanged(from:) で isTextInput == true のとき scheduleRecomputeVisible(coalesceMs: 150) を使う。 スライダー/テキスト入力の連続発火を間引く。 toggle 系（rating/label/cameraOnly/excluded*/kinds/flatten）は即時のまま。

2. 述語の適用順序の最適化

matches() の評価順を「コスト昇順 + 選択率高い順」に並び替え。 rating / label は Set O(1) で軽く、かつユーザー的に選択率が高い（絞り込み量が多い）。 date / shutter / nameSearch(caption) は後ろに。

3. filterKinds 変更のみ S1 再計算

onFilterChanged で repsAffected == true のとき mark(reps: true)、 それ以外は mark(filtered: true) にする。 flatten / filterKinds 変更以外で S1（全グループ走査）をスキップできる。 PR3 のメモ化と組み合わせると S1 コストがほぼゼロになる。

4. available* と buckets の分離

availableExtensions/Cameras/Lenses/Artists はメタデータ到着時に更新すれば十分 （フィルタ変更で変わらない）。buckets（ヒストグラム）はフィルタ変更後に coalesce で更新。 2 つの dirty キーに分けると不要な計算をさらに削減できる。
